# 수동 접근성·실기기 검증 증빙 레지스트리

> 상태: **검증 미완료**. 이 문서는 자동 감사 결과가 아니라, 실제 장비·보조기술에서 수행한 수동 검증의 최소 증빙을 기록하는 템플릿입니다.
> 개인정보, 설문 원문·점수, 전화 상대방 정보, 화면 녹화의 민감 내용은 기록하지 않습니다.

## 범위와 한계

- 자동 감사는 수동 접근성 검증을 대신하지 않습니다. W3C도 자동 도구만으로 접근성 충족 여부를 판정할 수 없다고 안내합니다.
- 이 레지스트리에 `PASS`를 기록하는 것은 해당 시나리오의 실제 시험 기록일 뿐이며, 임상 타당화·법무 검토·전문가 승인이나 접근성 적합성 인증을 의미하지 않습니다.
- 검증자는 실제 장비와 배포 후보 빌드에서 수행하고, 실패는 조치·재시험 전까지 최신 결과로 남깁니다.

## 기록 규칙

### 수동 검증 범위 해시

아래 값은 접근성·위기 동선·오프라인/PWA 자산을 포함한 현재 배포 범위의 해시입니다. 실제 장비 시험을 마친 뒤에만 현재 값으로 갱신합니다. 값이 바뀌면 이전 수동 `PASS` 기록은 재검증 전 배포 준비도에 사용할 수 없습니다.

- 수동 검증 범위 해시: `기록 전`

각 행은 다음을 모두 채웁니다.

- 기록 ID: `A11Y-YYYYMMDD-설명자` 형식. 날짜는 기록일과 일치해야 합니다.
- 검증자: 개인 이름 대신 역할만 기록합니다(예: `접근성 QA`, `제품 책임자`).
- 환경: OS·브라우저·보조기술과 버전, 또는 실제 기기/전화 앱의 종류를 적습니다.
- 시나리오: 아래 허용 코드 중 하나를 정확히 사용합니다.
- 결과: `PASS` 또는 `FAIL`만 사용합니다. `FAIL`이면 조치 티켓/문서 식별자를 적습니다.
- 재검증: 가장 최근 유효 기록이 `PASS`이고 기록일이 180일 이내여야 배포 준비도 게이트를 통과할 수 있습니다. 같은 날짜에 `PASS`와 `FAIL`이 공존하면 `FAIL`이 우선합니다. 존재하지 않거나 미래인 날짜는 유효하지 않습니다.

| 기록 ID | 기록일 | 검증자 역할 | 환경 | 시나리오 | 결과 | 이슈/조치 식별자 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

## 필수 시나리오 코드

| 코드 | 실제로 확인할 최소 범위 |
|---|---|
| `NVDA` | Windows + NVDA에서 인트로, 설문, 위기/결과의 제목·포커스·라디오·라이브 리전 |
| `VOICEOVER` | macOS 또는 iOS + VoiceOver에서 핵심 위기 동선과 제어 이름/상태 |
| `TALKBACK` | Android + TalkBack에서 핵심 위기 동선과 제어 이름/상태 |
| `VIEWPORT-320` | 320 CSS px 폭에서 잘림·가로 스크롤·위기 CTA 접근성 |
| `ZOOM-200` | 200% 확대에서 잘림·포커스·위기 CTA 접근성 |
| `PHONE-APP` | 실제 기기에서 위기 번호 전화 링크가 전화 앱으로 넘겨지고 실패 안내를 확인 |
| `OFFLINE-CRISIS` | 설치/캐시된 PWA의 오프라인 위기 안내·전화 링크를 실제 환경에서 확인 |

## 배포 전 확인

- [ ] 7개 필수 시나리오의 최신 유효 기록이 모두 `PASS`이고 180일 이내이다.
- [ ] 발견된 접근성·기기 문제의 조치와 재검증 기록이 연결되어 있다.
- [ ] 증빙에 개인정보·설문 응답·통화 상대방 정보가 포함되지 않았다.
- [ ] 배포 책임자가 증빙의 범위와 한계를 검토했다.

`npm.cmd run manual:check`은 형식·시나리오 누락·최근 실패·유효기간·현재 범위 해시만 검사합니다. 실제 수행 사실과 접근성 적절성은 사람이 검토해야 합니다.
